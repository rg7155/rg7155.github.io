플레이링스

클라이언트 프로그래머 · 2023.03(산업기능요원 입사) ~ 재직 중
소셜 카지노 슬롯 라이브 서비스 · Cocos2d-JS · 신규 슬롯 약 20종
현재 팀은 Cocos Creator로 엔진 이전 초기 단계

슬롯 개발 방식

프로젝트 규칙과 슬롯 도메인 지식을 문서로 쌓아 두고, 코드를 쓰기 전에 AI가 기획서와 아트 리소스, 서버 코드를 먼저 대조하게 합니다. AI가 모르는 새 기획 요소는 제가 판단해서 문서에 추가합니다.

슬롯 하나는 보통 8주 동안 만듭니다. 사전 검증에서는 리소스 오타나 기획 오류를 개발 전에 찾아 해결합니다. 개선 회의에서는 연출과 아트 피드백을 반영하고, 룰이 바뀌면 개발 가능 여부를 확인합니다. 회의에서 직접 아이디어도 냅니다. 코드는 대부분 AI가 작성합니다.

신규 슬롯과 함께, 오래된 슬롯의 룰을 조금 바꾸고 코드를 공용 모듈로 옮기는 리워크도 맡습니다.

이슈 해결: 웹에서만 다른 이미지가 나오던 문제

AI를 쓰기 전, 팀원이 막힌 이슈를 처음으로 제가 풀어 준 일이라 기억에 남습니다.

  • 웹에서만 엉뚱한 이미지가 나옴. 에러도 로그도 없음
  • 엔진은 이미지를 이름 하나로 관리해서, 이름이 겹치면 먼저 등록된 쪽을 씀. 그래서 이름 중복부터 의심했지만 웹 리소스에는 중복이 없음
  • 엔진에 로그를 넣어 실제로 불러오는 리소스를 출력
  • 공통 시스템 코드가 웹에서 모바일 리소스까지 불러오고 있었고, 모바일 아틀라스에 같은 이름의 이미지가 있었음
  • 겹치는 이름을 고쳐 해결하고, 원인을 팀에 바로 공유함

Rewind Survivors

탑다운 2D 서바이버 · Unity 6 · 1인 · 2026.04 ~ 09 · WebGL 배포
▶ 브라우저에서 플레이

회사에서는 Cocos2d-JS만 써서, 상용 엔진으로 끝까지 만든 게임이 없었습니다. Unity로 배포까지 해 보고, AI로 어디까지 만들 수 있는지도 알고 싶었습니다. 코드는 대부분 AI가 썼습니다.

  • 장르: 몰려오는 적을 피하며 버티는 서바이버. 즐겨 하던 탕탕특공대를 참고
  • 핵심: 시간 되돌리기. 위험할 때 쓰면 플레이어와 적이 5초 전 상태로 돌아감

시간 되돌리기: 풀에서 다시 꺼낸 적을 구분하기

0.05초마다 플레이어, 적, 웨이브, 보스 상태를 기록해 두고, 되돌릴 때 최신 기록부터 거꾸로 적용합니다. 기록은 100칸짜리 원형 버퍼에 담아, 오래 플레이해도 칸이 늘지 않게 했습니다.

문제는 적을 오브젝트 풀로 재사용한다는 점이었습니다. 풀에서 다시 꺼낸 적은 5초 전과 같은 오브젝트지만 다른 적입니다. 기록을 그대로 덮으면 죽은 적의 상태가 엉뚱한 적에게 씌워집니다.

  • 적이 생길 때마다 새 ID를 주고, 기록도 ID로 남김
  • 되돌릴 때 ID를 비교해 셋으로 나눔. 양쪽에 있으면 상태만 복원, 기록에만 있으면 부활, 지금만 있으면 풀로 반환
  • 같은 구조에 보스의 패턴 순서와 체력도 얹음

AI에게 맡겼다 실패한 탐험 모드

생존 모드를 완성한 뒤 탐험 모드를 붙였습니다. 기획은 얕게만 정하고 나머지는 AI에게 맡겼는데, 화면이 그럴듯하게 나올 때마다 조금씩 고쳐 달라고 하다 보니 게임이 점점 이상해졌습니다. 시야가 좁아 세로 화면을 가로로 바꿨고, UI 배치도 처음부터 다시 정해야 했습니다. 무엇을 만들지, 아트 방향은 무엇인지 정하지 않고 시작한 게 원인이었고, 탐험 모드는 접었습니다.

딱지왕

▶ 개발 중 영상 youtu.be/W_WeZbZFWYY

  • 게임: 딱지를 쳐서 뒤집고, 연쇄로 점수를 쌓아 보스와 겨룸
  • 진행: 첫 구역과 첫 보스까지 완성. 아트는 대부분 임시. Steam 출시 목표

기획 먼저

Rewind의 탐험 모드처럼 화면을 보며 고쳐 나가다 실패하지 않으려고, 코드보다 게임 규칙을 먼저 문서로 정리했습니다. 방향, 범위, 조작 방식처럼 사람이 정해야 할 것은 직접 결정하고 기록했습니다.

코드 대신 검증

코드는 AI가 쓰고, 결과는 코드 검토보다 자동 테스트로 확인합니다.

  • 테스트: 판정이 규칙 문서대로 나오는지 확인
  • 같은 판 재현: 데일리 도전과 리플레이는 같은 입력에서 항상 같은 판이 나와야 함. 그래서 판정 규칙을 Unity와 분리하고 정수로만 계산

직접 플레이해 보고 뺀 규칙

AI와 함께 쓴 기획서에는 벽에 막힌 바람이 튕겨 나와 딱지를 뒤집는 벽 반사 규칙이 있었습니다. 구현까지 했지만, 직접 플레이해 보니 반사가 일어나는 걸 알고 봐도 눈에 띄지 않았습니다.

  • AI에게 원인을 분석하게 하니, 실제 딱지치기에 없는 개념이라 화면에 단서가 없고 효과도 작고 드물었음
  • 규칙의 출처를 찾아보니 AI가 쓴 기획서 초안뿐이었고, 제가 결정한 기록은 없었음
  • 규칙을 빼고 규칙 문서, 판정 기준, 게임 코드를 함께 정리함. 예전 기록이 다르게 재생되므로 기록 버전을 올림

비슷한 아이디어도 재미를 확인하기 전에는 만들지 않고 후보로만 남겼습니다. 손맛처럼 자동 테스트로 알 수 없는 것은 계속 직접 플레이하며 확인합니다.

렌더링

  • 같은 파이프라인 상태를 쓰는 물체를 묶어 상태 변경 횟수를 줄임
  • ③림 라이트, 깊이 안개, 디졸브를 비트마스크로 켜고 끔
  • ④칼 손잡이와 칼끝 좌표를 매 프레임 기록하고, Catmull-Rom 보간으로 이어 소드 트레일을 그림

맵 충돌

맵은 Unity에서 배치해 파일로 내보내고, C++에서 읽어 씬을 구성했습니다. 플레이어와 맵의 충돌 방식은 세 번 바꿨습니다.

  1. ①맵 메시를 감싸는 OBB와 충돌: 빠르지만 메시 모양과 달라 세밀하지 않음
  2. ②맵 메시 표면(삼각형)과 구 충돌: 세밀하지만 검사가 많아 프레임이 떨어짐
  3. ③충돌 전용 박스를 따로 배치해 OBB 충돌: 검사 수가 줄어 빠르고 적당히 세밀함. 대신 박스를 일일이 배치해야 함
